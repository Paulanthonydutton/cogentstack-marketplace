# Use CogentStack

Resolve the current ChatGPT Project with `scripts/project-context.ps1`. The helper derives a one-way, non-secret context key from the stable ChatGPT Project worktree identity when available. Pass that context through every workspace and protected Desktop request. Each context has independent selected-contract, Contract Runtime, current request, active project, deletion, Git, preview, and deployment state while the completed-project library remains shared. If the host provides no stable project identity, use the explicit legacy default and never guess from a conversation title.

The normal browser launcher reuses one physical CogentStack tab. When the current ChatGPT Project differs from the remembered context, restore the prior split, navigate that exact reused CogentStack tab to the new context URL, and rebuild the verified split. Do not create one permanent browser tab per ChatGPT Project and do not inspect or cycle unrelated tabs.

CogentStack's public plugin reuses an existing CogentStack workspace or home tab in a normal Google Chrome or Microsoft Edge window, navigates a home tab to the hosted workspace when needed, and presents that same tab in a reversible page-only right panel beside the visible ChatGPT or Codex window. The launcher first resolves the remembered, previously verified workspace window. With no usable remembered state, Windows accessibility inventories tab titles without selecting them, accepts only the exact CogentStack workspace or home titles, activates at most one chosen candidate, and then verifies that candidate's address. It never uses a generic title-contains-CogentStack match, never cycles through unrelated ChatGPT, Claude, installation, account, or legal tabs, and restores the originally selected tab if address verification fails. Concurrent launch requests are serialized before this resolution, so a repeated invocation observes the shared workspace tab instead of racing to create another one. Only when no exact workspace or home candidate exists does the registered browser open the exact hosted URL once as a normal tab rather than creating a separate app-mode session. The launcher temporarily removes the browser frame, positions its controls outside the work area, and clips the window to the measured web document so the CogentStack page—not Chrome's retained edge or a second session—fills its complete half. It does not use monitor-wide F11. A white backdrop covers the Windows work area behind the equal-width panels and remains visible as a narrow vertical divider with matching two-pixel neutral-grey rules at the desktop edge and the CogentStack edge, separated by visible white space. The launcher verifies that both panels remain above that backdrop; if the backdrop would cover either panel, it rejects the split and restores the ordinary layout. The companion-only X in the workspace header returns that same tab to the CogentStack home page, restores the normal browser frame, maximizes that ordinary browser window, restores ChatGPT or Codex, and removes the backdrop. If another action navigates the reserved companion tab away from CogentStack, the same exit watcher immediately removes the crop and restores the ordinary maximized browser instead of trapping the foreign page in companion mode. The plugin does not distribute contracts, task blueprints, compatibility rules, licence validation logic, or a local project generator. The protected server produces a request-bound project artifact; Desktop verifies and writes only that artifact.

1. The plugin package and unprotected workspace browsing are public, but protected credentials and project-changing actions are not. Never collect legal acceptance, a CogentStack login, licence key, activation code, or Desktop credential in ChatGPT or Codex. The installation prompt's opaque, single-use reference is the only permitted handoff from the website: it binds the website's signed-in account and explicit legal confirmation to this Windows installation, is consumed during installation, and must never be printed or requested again. The resulting DPAPI-protected installation credential renews the private Desktop connection without another legal confirmation while this remains the active installation. Only one ChatGPT or Claude Desktop installation may be active for the account at a time.
2. Treat `$cogentstack`, `@cogentstack`, a CogentStack plugin mention, or a natural-language request to open CogentStack as the same launch request. Every invocation must run this complete sequence; do not stop after checking backend readiness.
3. Run `scripts/ensure-cogentstack.ps1 -Mode Companion` exactly once. Read its compact JSON and require `status: ready`, `mode: companion`, and the official `https://cogentstack.app/stack?surface=chatgpt` URL. Never remove the surface marker or fall back to `/app`, localhost, a bundled web server, or a manually created browser tab.
4. On Windows, run `scripts/hide-codex-sidebar.ps1` exactly once before arranging the windows. Treat `hidden` or `already_hidden` as success. If the helper reports that the ChatGPT/Codex window is unavailable or ambiguous, state that the sidebar could not be hidden automatically, then continue the companion launch without claiming a complete visual match.
5. Immediately run `scripts/open-cogentstack-companion.ps1 -Mode Open -Url <exact returned URL>` exactly once. This serializes concurrent launch requests and resolves the remembered verified workspace first. If remembered state is unavailable, it inventories exact workspace and home titles without selecting tabs, activates at most one candidate, verifies that candidate's CogentStack address, navigates a verified home tab to the exact workspace URL when needed, and reuses its owning normal browser window. It must not use substring title matching or inspect tabs by activating them. It must ignore pending or completed installation, account, legal, ChatGPT, Claude, and other unrelated tabs. If the chosen exact-title candidate fails address verification, it must restore the original tab, return `opened_unarranged`, and open nothing else. Only when no exact workspace or home candidate exists may it open the exact URL once as a normal tab in the registered browser; it must never create a separate `--app` or `--new-window` session. Require `tabResolution: remembered-workspace` or `tabResolution: exact-title-inventory` when a tab was reused, require `candidateTabsActivated` to be at most `1`, and require `reusedExistingTab: true`, `reusedExistingHomeTab: true`, and `openedNewTab: false` when a home-page tab was reused. The helper creates a white work-area backdrop above the Windows desktop and behind both companion panels, selects the foreground ChatGPT or Codex window, temporarily makes the reused browser frame borderless, positions its browser controls outside the work area, and applies a reversible window-region crop to the measured web document bounds so Chrome's retained edge is not visible. The browser-chrome height measured before cropping remains authoritative if accessibility briefly reports the scroll region instead of the whole document, preventing the CogentStack banner from being cut off. It then verifies an equal-width 50/50 split and the visible `CogentStack home` header anchor: ChatGPT or Codex on the left, the CogentStack page on the right, a passive 12-pixel white vertical divider with matching two-pixel neutral-grey rules at the desktop and CogentStack edges, separated by eight pixels of white space, aligned top edges, and full work-area height. The divider is anchored behind the CogentStack browser so it remains visible in the gutter when a screenshot tool has focus while other windows cover it naturally. The divider may mask the two panel-edge shadows only while the split geometry and header remain verified; it must hide immediately if either panel is maximized, moved, or otherwise leaves that geometry, and Resume must rebuild a disturbed split or clipped header. It must report `browserContentMode: page-only`, `browserChromeHidden: true`, `browserContentClipped: true`, `headerVisible: true`, `gutter: 12`, `separated: true`, `whiteDivider: true`, `dividerEdgeVisible: true`, `dividerMasksShadows: true`, and `workspacePanelsAboveBackdrop: true`; it must not send F11 or use monitor-wide browser fullscreen. Treat `arranged` with `layoutVerified: true` and `headerVisible: true` as fully positioned and `opened_unarranged` as not safely positioned. If it returns `browser_unavailable`, explain that Google Chrome or Microsoft Edge must be installed for the companion flow. Do not silently fall back to an embedded Codex panel.
6. Treat `accountState` as the only launcher evidence about the selected page. Report a logged-in state only when it is `signed_in`; if it is `signed_out` or `unknown`, say so without guessing. Never copy cookies or credentials between Chrome, Edge, Codex, or another browser profile. Report the browser named by the helper instead of assuming Chrome or Edge.
7. Do not call `codex_app__open_in_codex`, do not launch a browser app window, and do not create or retry tabs when an exact workspace or home tab was found. Do not clean up, select, close, or repurpose installation or unrelated tabs during a normal launch. This keeps isolated sessions, queued panel mounts, visible tab cycling, and duplicate workspace tabs out of the normal flow.
8. Treat the hosted workspace as authoritative. Do not infer, recreate, cache, or disclose proprietary contract content, project-generation rules, subscriber credentials, or protected service responses.
9. Contract activation, validation, project-artifact generation, and next-action decisions are executed by CogentStack's protected server-side Contract Runtime. Never request or download a complete contract, task blueprint, or Contract Pack. Consume only the narrow result presented by the hosted workspace or the request-bound generated files returned to the fulfilment helper.
10. A hosted selection alone does not authorize local changes. Local project creation is allowed only after the user approves the exact target directory and submits a project request in the hosted workspace, then describes what they want built in the adjacent composer. That brief is the explicit fulfilment instruction. Do not require a new task or a fixed command.

When the user selects the companion-only X in the workspace header, the page navigates that reused tab to the CogentStack home page and the launcher's local exit watcher clears the temporary crop, restores the normal browser frame, maximizes that browser with Windows `SW_MAXIMIZE`, restores the remembered ChatGPT or Codex position, removes the backdrop and divider, and clears fast-resume state. The adjacent minus control navigates the same workspace to `companion=suspend`; the watcher removes the crop, restores and maximizes the normal browser, restores ChatGPT or Codex, hides the backdrop and divider, and preserves only the exact local window handles, original rectangles, browser style, workspace URL, and layout status required for fast resume. It performs that same suspension whenever the selected companion window acquires a non-empty address outside `cogentstack.app`, including an expanded localhost project preview. The normal launch installs a Start-menu shortcut named **CogentStack Work Mode (Codex)**. Its local `Toggle` mode suspends an active layout or uses `Resume` to reselect the remembered CogentStack workspace tab in the exact browser window and rebuild the verified 50/50 layout without readiness, login, licence, legal, or tab-creation work. If either remembered window or that workspace tab is gone, it reports `cold_start_required` and tells the user to invoke `$cogentstack`; it must never guess or create a replacement. This is ordinary window maximization, never browser F11 fullscreen. When the user asks in the adjacent composer to hide, suspend, resume, toggle, or close the companion, run `scripts/open-cogentstack-companion.ps1` once with the corresponding `-Mode`. Hide preserves fast-resume state without maximizing; Suspend preserves it and maximizes the browser; Close performs the full exit and clears it. None closes the user's reused browser window.

The companion header presents **−**, **+**, and **X** in that order. Minus suspends the split while keeping the watcher alive; plus navigates the same CogentStack page to `companion=resume`, which the local watcher converts directly back into the verified 50/50 layout; X performs the full exit. The user must not need the Start menu or another `$cogentstack` invocation for the normal collapse-and-restore cycle.

The reversible layout state retains the original window style and position so every suspend or full exit can restore the ordinary desktop safely.

### Companion layout acceptance

The crop's top edge must remain at the real browser-window top while the controls stay physically above the work area. Require `browserTopCropRemoved: true`; this prevents later Chrome accessibility reflow from clipping the CogentStack banner or X control. If banner, crop, divider, or split acceptance fails, require `layout_rejected` or `resume_rejected` and confirm that the ordinary maximized browser and ChatGPT/Codex layout were restored rather than leaving an unverified companion active.

## Keep the workspace inside Codex

Use the embedded mode only when the user explicitly asks to keep CogentStack inside Codex or requests the native right panel. Explain first that this panel has an isolated browser session: it does not inherit the user's Edge, Chrome, or system-browser CogentStack login, but a current account-bound installation can issue its short-lived panel session without a second legal confirmation.

1. Run `scripts/ensure-cogentstack.ps1 -Mode Embedded` exactly once and read its compact JSON.
2. When it returns `status: ready`, call `codex_app__open_in_codex` exactly once with its exact returned URL as `target.url`, `target.type` set to `browser`, and `placement` set to `right`. The URL may contain a short-lived `#desktop=` fragment when a prior Desktop authorization was refreshed; never print, copy, log, alter, or remove that fragment.
3. Treat either `opened` or `queued` as an accepted host mount request. Do not create browser tabs, pass `tabId`, open a blank tab, or retry the panel call.
4. Run `scripts/hide-codex-sidebar.ps1` only after the host accepts the embedded open request.
5. If `authenticated` is false, run `scripts/connect-cogentstack.ps1 -Mode status` once. A bound installation may renew itself and should then be retried once. If it remains signed out, state that the panel is public/signed out and that a fresh website installation request is needed. Never describe it as inheriting the normal browser login.

## Recover the account-bound installation

When the user explicitly asks to authorize, reconnect, or sign in to the embedded Codex panel:

1. Run `scripts/connect-cogentstack.ps1 -Mode status` once. A local credential file alone is not proof that the connection remains active; status verifies it against the protected service and automatically rotates an expired access token from the same installation's DPAPI-protected renewal credential.
2. If status is `connected`, run `scripts/ensure-cogentstack.ps1 -Mode Embedded` once and open its exact returned URL once inside Codex as described above. Do not ask for login, licence information, an authorization code, or another legal confirmation.
3. If status is `signed_out`, do not run the legacy `start` or `complete` modes and do not open `/activate`. Explain the returned reason. Only a deliberately new request from `https://cogentstack.app/install` may replace or repair the installation; that website path records the user's fresh tick and binds it to the new installation request.
4. The encrypted Desktop access and renewal credentials remain bound to the current Windows user through DPAPI. Never read, decrypt, display, or transmit them except through the connection helper and CogentStack's protected API flow.

When the user explicitly asks to sign out or disconnect the embedded Codex panel, run `scripts/connect-cogentstack.ps1 -Mode disconnect`. This revokes the server token before removing the encrypted local credential. The browser companion's normal website session remains separately controllable from the CogentStack account page.

## Create from the adjacent composer brief

When the user describes the project they want after recording an approved creation request in the hosted workspace:

1. Run `scripts/fulfil-project.ps1 -Mode inspect`. It uses the current user's DPAPI-protected Desktop credential internally and returns only narrow project-request summaries.
2. If inspection returns `desktop_authorization_required`, the approved hosted request is preserved. Do not tell the user to repeat sign-in, licence activation, Project Type selection, contract setup, directory approval, or Step 2. Do not request legal acceptance at this recovery point. Run `scripts/connect-cogentstack.ps1 -Mode status` once. If it reports `connected`, the same installation has renewed its private credential; retry inspection immediately.
3. If status remains `signed_out`, do not open the separate `/activate` flow. Explain that this installation is legacy, was explicitly revoked/replaced, or needs acceptance of updated legal documents according to its returned reason. The existing project request remains saved. Direct the user to `https://cogentstack.app/install` only in that case; its deliberately new installation request requires a fresh tick and will replace any other active Desktop installation. After that account-bound installation completes, retry inspection without recreating or altering the hosted project request.
4. The hosted workspace returns only its current authoritative request. If exactly one request is available, use it for the adjacent composer brief without asking the user to identify or repeat the project name. If no request is available, explain that the user must finish and approve Step 2 in the hosted workspace. If more than one request is ever returned, report a CogentStack service-state error; never ask the user to choose among stale requests.
5. Run `scripts/fulfil-project.ps1 -Mode create -RequestId <approved UUID>` for the one selected request. When there is exactly one request, `-RequestId` may be omitted.
6. The helper must keep the Desktop token, execution grant, and raw server artifact private. Never print, summarize, cache, or reproduce them. Do not substitute local templates, infer missing contract content, or bypass artifact checks.
7. The helper writes only beneath the server-returned target path, verifies every file and the whole artifact, installs dependencies, runs the generated acceptance tests, creates the initial Git baseline, and reports completion to the server. If it fails, do not delete the partial target; report its path and the failure clearly.
8. On success, report the exact target path, passed tests, and baseline commit. Then continue in the same task by treating the user's composer text as the project brief. Work only inside the created target, follow its generated repository instructions and acceptance checks, and verify the requested work. Do not push, deploy, commit beyond the generated baseline, or change any other repository unless the user explicitly asks.

After opening the workspace, display a brief welcome explaining which browser window was reused, the reported `accountState`, that Project Types can be browsed freely, sign-in or a licence is requested only when a contract is used, and the user can stay in the same task and write their project brief in the adjacent composer after approving Step 2.

## Restore portable knowledge for an existing project

Every newly generated project contains `AGENTS.md`, `PROJECT_KNOWLEDGE.md`, `CURRENT_STATE.md`, `HANDOFF.md`, `docs/decisions/`, and `.coge/knowledge-manifest.json`. These files carry durable, reviewable project knowledge in Git. Protected contract state remains on CogentStack and is restored through the manifest's safe project request identifier; credentials and proprietary contract contents must never enter the repository.

When a user loads or edits an existing project from a different ChatGPT Project:

1. First load that project in the hosted **Edit project** view for the current logical context.
2. Run `scripts/project-knowledge.ps1 -Mode inspect` exactly once. It accepts only the protected context's exact active target path, verifies that the request ID in `.coge/knowledge-manifest.json` matches the server record, reads only the bounded portable knowledge files, and reports the local Git branch, revision, dirty state, changed paths, and whether an origin is configured.
3. Read the returned knowledge before proposing or making project changes. Conversation history is optional context, not the project record.
4. Do not run `git pull` automatically. If source synchronization is needed, show the branch, revision, dirty state, and intended Git action; fetch or fast-forward only after the user explicitly asks for that Git action. Never overwrite dirty work.
5. Before an explicitly approved commit or handoff, run `scripts/project-knowledge.ps1 -Mode refresh` to update `.coge/knowledge-state.json`, and update the human knowledge files when decisions, architecture, tests, current state, risks, or outstanding work changed. This refresh never commits or pushes by itself.
6. A project created before this architecture may report `portable knowledge` missing. After the user explicitly asks to make that loaded project portable, run `scripts/project-knowledge.ps1 -Mode initialize` once. It creates only missing knowledge files, refuses to overwrite existing documents, marks unverified historical gaps, and does not commit or push. Review and complete that pack from repository evidence and user confirmation before treating the project as portable; do not invent historical decisions from Git alone.

## Generate or restart the active project preview

The hosted **Edit project** page remembers the last verified local preview address and presents its own **View project** button while that exact preview remains live. Routine viewing must use that button; it must not invoke Codex, rerun readiness, relaunch the companion, or start another preview process.

When the user explicitly says `@cogentstack view active project`, treat the command as preview generation or recovery only:

1. Run `scripts/generate-project-preview.ps1 -Mode generate` exactly once. Do not open a browser tab or navigate the reserved CogentStack companion tab to localhost.
2. The helper obtains the sole active project through the protected service, accepts only its exact absolute target path, and first looks for an already-running preview that is both healthy and owned by a process tree containing that exact project path. It must never trust a stale port, arbitrary localhost service, conversation-supplied path, or process ID.
3. If no matching preview is running, the helper may start only the exact active project's `scripts/start-local.ps1`. It should prefer the project's remembered port when available, but it must verify the resulting listener, process ancestry, health response, and project path before reporting it.
4. Treat only `status: generated` or `status: already_running` together with `remembered: true` as success. The helper records the live loopback URL with CogentStack and starts a quiet heartbeat. The hosted page then exposes the direct **View project** button without requiring the command again.
5. If it reports `desktop_authorization_required`, run `scripts/connect-cogentstack.ps1 -Mode status` once. If that renews the current account-bound installation, retry preview generation once. Do not ask for login, licence details, legal confirmation, an authorization code, a path, or a port.
6. If it reports `no_active_project`, tell the user to load the project on **Edit project**. If it reports `preview_not_supported`, explain that the active project has no governed local preview launcher. Do not improvise a generic server.

The heartbeat deliberately marks a stopped preview unavailable while retaining its last safe port for the next generation. A browser-facing runtime is considered live only while its verification is fresh; remembering a port is never treated as proof that a process is still running.

## Delete an approved project and folder

Typing the exact project name and selecting **Delete project and folder** in the hosted **Edit project** page is the single explicit deletion confirmation. In companion mode, the page signals the authenticated local watcher, which normalizes Chrome or Edge address-bar text even when accessibility omits the `https://` scheme and processes the approved deletion before any layout monitoring. It runs `delete-project.ps1 -Mode delete` against the sole server-authoritative request without requiring a second composer command. The watcher returns the same tab to the clean workspace URL when the operation finishes. A manual adjacent-composer deletion request is a recovery path only when that automatic handoff was unavailable.

When recovering an already approved deletion from the adjacent composer:

1. Run `scripts/delete-project.ps1 -Mode inspect`. It returns only the current authoritative deletion request.
2. If no request is available, explain that the user must approve deletion on the **Edit project** page first. If more than one request is ever returned, report a CogentStack service-state error; never choose among deletion requests.
3. Run `scripts/delete-project.ps1 -Mode delete -RequestId <approved UUID>` for the sole request. When exactly one request exists, `-RequestId` may be omitted.
4. Never delete the path manually or substitute a path from conversation context. The helper accepts only matching server-returned deletion and project IDs, the exact registered child path, approved parent directory, project slug, and short-lived execution grant. It refuses drive roots, temporary validation paths, files, reparse points at the parent, target, or nested levels, and mismatched parents or folder names.
5. Treat success as proven only when the helper returns `status:deleted`. On failure, report the requested target, `folderRemoved`, `registrationFinalized`, and whether a partial folder remains. If the folder was removed before server acknowledgement failed, say that the filesystem deletion is already permanent even though registration was not finalized. Do not retry without a fresh hosted approval.
6. On success, report the exact deleted target and `folderRemoved`. If it is false, say that the folder was already absent; never claim it was removed. State that the folder, preview watcher, project registration, active-project selection, runtime and Git snapshots and requests, Deployment Packs, contract-compilation measurements, project-bound Contract Runtime session, and the deletion request itself are permanently removed and unrecoverable.

## Prepare an independent deployment handoff

Use this flow only after the user selects a completed project in the hosted **Hosting** tab and presses **Generate Deployment Pack**.

1. Inspect the approved request with `scripts/prepare-deployment.ps1 -Mode inspect`.
2. Prepare the fixed handoff files with `scripts/prepare-deployment.ps1 -Mode prepare -RequestId "<request-id>"`.
3. Report the exact project folder, the generated `DEPLOYMENT.md` and `deployment.manifest.json` files, and the approved non-secret repository/host target recorded in them.
4. Do not push or connect during pack preparation. A destination recorded in the manifest is not permission to use it.
5. If the user subsequently and explicitly asks to deploy to that target, read the local manifest, show the exact repository, branch, host, port, deployment directory, health URL and planned local actions, then obtain confirmation that those exact targets are approved.
6. Use only the local machine's existing Git credential helper, SSH configuration and SSH agent. Never request, print, store, copy into the manifest, or transmit passwords, access tokens, private keys or agent material.
7. Before the first SSH connection, compare the live host key with the approved fingerprint. Stop on a missing or mismatched fingerprint unless the user independently verifies and explicitly approves the new key.
8. Keep execution bounded by the manifest: push only the approved branch and repository; connect only to the approved host and port; write only beneath the approved deployment directory; run the documented build, health and release checks; produce rollback instructions and record the deployed source revision.
9. Direct the user to the hosted **Changes** tab for ordinary source-history actions that are not part of the explicitly approved deployment.
